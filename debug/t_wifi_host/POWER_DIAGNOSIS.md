# COM11：与发射功率相关的 Wi-Fi 认证失败

2026-10-28 使用 COM8 监听、COM11 故障板的 19 dBm 请求上限复测见
[详细抓包报告](POWER_CAPTURE_20261028.md)，附归档 PCAP、原始日志、时间线及逐帧统计。

测试日期：2026-10-27。故障板 COM11，STA `38:44:be:c9:d7:d0`；
监听板 COM10，MAC `1c:29:04:22:b1:38`。

## 已证实的结论

**故障与 Wi-Fi 发射功率设置有可重复的相关性。** 对同一块板、同一热点，
上限 19.5 dBm / 10 dBm 时认证失败；上限 2 dBm 时认证、关联可完成。
按低→高→低顺序复测，认证成功→失败→成功，说明不是仅靠等待或重新校准恢复。

这是故障范围的定位，尚不能仅凭软件日志认定某颗稳压器、电感或芯片损坏。
首要硬件假设是射频发射时供电异常，其次是匹配/负载导致高功率发射质量异常。
需要电源波形或 RF 测量才能区分。

## 实验控制条件

- 热点 `zhanglazhuan`，BSSID `42:d1:33:36:96:51`，WPA2，信道 1。
- 同一份本地凭据；不打印密码。
- COM10 固定信道 1，按故障板 MAC 和热点 BSSID 过滤，RAW 开启，snaplen 256。
- 每个功率设置均测试 DeepStoa 配置和 ESP-IDF 默认配置。
- 临时工程复制现有 `t_wifi` 源码，仅增加功率循环和日志，强制完整 RF 校准
  `CONFIG_ESP_PHY_RF_CAL_FULL=y`（校准模式 2）。第二轮跳过 Internet 测试。
- 通过 `esp_wifi_set_max_tx_power()` 设置，再通过 `esp_wifi_get_max_tx_power()`
  验证设置值。参数单位 0.25 dBm；它是发射功率上限，不是仪器测得的实际 RF 输出。
- 下文 19.5 / 10 / 2 dBm 均指 API 请求值。后续核对 ESP-IDF v5.5.3 文档发现其
  存在离散档位映射：78 → 72、40 → 34、8 → 8（单位 0.25 dBm），
  因此不能将这些请求值或原样读回值视作精确的实际射频输出。
- 临时源码和镜像在 `build/tx_diagnostic/`。测试后 COM11 恢复原 `t_wifi/build_slow`
  测试镜像；COM10 保留监听固件。没有执行整片擦除、NVS 擦除或 eFuse 写入。

## 第一轮：完整校准 + 19.5 / 10 / 2 dBm

原始日志目录：[capture_20261027_174307](build/capture_20261027_174307/)。

| API 设置 | 发射功率上限 | DeepStoa 配置 | IDF 默认配置 |
| --- | --- | --- | --- |
| 78 | 19.5 dBm | 认证超时，reason=2 | 认证超时，reason=2 |
| 40 | 10 dBm | 认证超时，reason=2 | 认证超时，reason=2 |
| 8 | 2 dBm | 认证、关联、获取 IP，ping 4/4 | 认证、关联、获取 IP；后续 DNS 失败 |

2 dBm 下监听板抓到了 STA→AP AUTH、AP→STA AUTH、关联请求/响应及 EAPOL。
这证明监听器能抓到目标认证帧，也证明故障板射频通路并非完全断开。
完整校准本身不能消除高功率失败。

关键证据：[COM11.log](build/capture_20261027_174307/COM11.log)、
[COM10.log](build/capture_20261027_174307/COM10.log)、
[sniffer.pcap](build/capture_20261027_174307/sniffer.pcap)。

## 第二轮：2 → 19.5 → 2 dBm 回切

原始日志目录：[capture_20261027_174540](build/capture_20261027_174540/)。

| 顺序 | 发射功率上限 | 两套配置的观测 |
| --- | --- | --- |
| 1 | 2 dBm | 均完成认证并触发 associated；15 秒内未拿到 IP |
| 2 | 19.5 dBm | 均在认证阶段 reason=2；没有 associated |
| 3 | 2 dBm | 再次均完成认证并触发 associated；15 秒内未拿到 IP |

注意第二轮的 `FAIL (15 s timeout)` 是等待 IP 超时，不能和高功率的认证失败混为一谈。
抓包中低功率存在报文重传，降低功率未能保证整条通信链路稳定，因此不是最终修复。
监听统计的软件队列丢包为 0；PCAP 转换无损坏 CAP 记录。

关键证据：[COM11.log](build/capture_20261027_174540/COM11.log)、
[COM10.log](build/capture_20261027_174540/COM10.log)、
[sniffer.pcap](build/capture_20261027_174540/sniffer.pcap)。

## 把根因落实到器件的测量顺序

1. **先确认 U5 实物型号。** 核对输出能力、压差、限流、输入供电及输出电容要求。
   Espressif 建议 3.3 V 供电能力至少 500 mA；这不是已测得的本板峰值电流。
2. **示波器对照 2 / 19.5 dBm。** 同时测 TP7 主 3V3、C19 非接地端（U7 pin2/3），
   必要时测 U5 VIN/VSYS。用短接地，观察认证发射瞬间；万用表平均电压不足以排除瞬态跌落。
3. TP7 与 C19 都跌落：优先查上游供电、U5 限流/压差/稳定性及 C6 等实际装配。
   TP7 稳定而 C19 跌落：优先查 L2 实物料值、直流电阻、焊点、走线和本地去耦。
   芯片数字供电未复位并不能排除这条模拟电源支路的异常。
4. 若两处电压都正常，交换已知良好天线，检查 U10、L3 及匹配网络，再测高/低功率下
   实际 TX 功率、频偏、EVM 和谐波；原理图无法证明 PCB 阻抗、器件装配和 PA 状态正确。

官方依据：[ESP32-S3 电源、晶振及 RF 设计要求](https://docs.espressif.com/projects/esp-hardware-design-guidelines/en/latest/esp32s3/schematic-checklist.html)。
该指南明确指出 VDD3P3 在发射时电流突增可能导致电源跌落，并要求关注去耦及供电滤波电感的电流能力。

用于复核的 eFuse 只读检查中，`VDD_SPI_FORCE=true`、`VDD_SPI_XPD=true`，
`VDD_SPI_TIEH` 指向 1.8 V LDO，未发现需要通过修改 Flash 电压 eFuse 解释本次功率相关故障的证据。

## 临时验证方法

Wi-Fi 启动后、首次扫描/连接前设置：

```c
ESP_ERROR_CHECK(esp_wifi_set_max_tx_power(8)); // 上限 2 dBm，仅用于诊断
```

它已在本板上改善认证阶段，但会降低覆盖能力，且第二轮仍有等待 IP 超时。
不能以这行配置替代对供电和射频通路的硬件检查。
