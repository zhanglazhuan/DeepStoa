- **1/42 次**高功率尝试观察到 AP 成功 AUTH 回复，出现于最初第一轮的第一次尝试。
- **42/42 次**高功率尝试最终失败。

结论：**成功 AUTH 回复尚不能稳定复现，新增 30 次没有重现；高功率认证失败可以反复复现。**
1/42 是本批观察比例，不是估计出的固定成功概率；无线环境未做屏蔽控制。

## 结论

**短接后仍不能在高请求功率档正常连接。** 两轮各执行
19→2→19→2→19 dBm，每档测试 DeepStoa 和 IDF 默认配置：

| 条件 | 第一轮 | 第二轮 |
| --- | --- | --- |
| 19 dBm 请求上限 | 6/6 认证失败，reason=2 | 6/6 认证失败，reason=2 |
| 2 dBm 请求上限 | 4/4 获取 IP | 4/4 获取 IP |

功率 API 请求/读回分别为 76/76 和 8/8，19 dBm 请求落在 IDF 文档的 18 dBm 档；
不是实测 RF 输出。热点仍为 `my_test_wifi`、BSSID `42:d1:33:36:96:51`，
WPA2、信道 1，故障板 STA `38:44:be:c9:d7:d0`。第一轮目标扫描约 -44 至 -41 dBm，
第二轮约 -44 至 -41 dBm。前后不是屏蔽环境，信号位置/干扰变化未被仪器控制。

## 新证据：第一轮首个高功率尝试出现 AP 成功认证回复

第一轮高功率 DeepStoa 尝试仍在认证阶段失败，但 COM8 抓到目标 AP 发往
故障板 STA 的 **63 条有效 AUTH 记录**，包含重传：

- COM8 接收回调时间：`6,357,421–6,540,795 us`，约 183 ms。
- 发送地址 `42:d1:33:36:96:51`，接收地址 `38:44:be:c9:d7:d0`。
- 全部 `alg=0 transaction=2 status=0`，即 Open System 成功认证回复。
- `seq=3334` 共 18 条、`seq=3335` 共 45 条；`retry=1` 为 61 条，另 2 条为 0。
- 该高功率尝试没有抓到 STA→AP AUTH，也没有后续关联请求。
- COM11 仍为 `init -> auth -> init`，约 1 秒后本地 `reason=2`。

原始示例：

```text
RX t=6357421us ch=1 rssi=-30 AUTH ra=38:44:be:c9:d7:d0 ta=42:d1:33:36:96:51 bssid=42:d1:33:36:96:51 seq=3334 retry=0 protected=0 len=30
AUTH direction=AP->STA alg=0 transaction=2 status=0 rx_callback_us=6357421 rx_hw_us=6881562 output_delay_us=24906
```

**按正常协议交互推断，这至少表明热点曾收到来自目标 STA 的认证请求并作出了回复，
尽管旁路监听漏掉了该请求。** 因而不能把本轮所有高功率失败解释成“请求根本没有发出或热点从未收到”。
该次最晚可观察到的步骤已推进到 **AP 发出成功 AUTH 回复**，但故障板没有进入关联。
可能是故障板未可靠接收/处理回复，或收发确认链路异常；重传本身不能确定哪一方向、哪个器件损坏。
本次未记录 ACK，不据此判定 ACK 是否真的发出/到达。

第一轮另外五次高功率尝试、第二轮全部六次高功率尝试，均未观察到目标双向 AUTH；
监听期间仍有目标 AP Beacon。两轮低功率均能观察到双向认证和后续关联。
AP 回复现象未在第二轮复现，不能宣称 L2 短接已经修复认证或稳定改善链路。

## 时间归属与记录质量

首轮 AUTH 密集输出产生了超过 2 秒的串口输出积压，但软件队列统计未见丢包。
如果按主机收到 CAP 的时间计数，会把第一次尝试的 AP 回复错误地归到第二次尝试。
本次以 CAP 内接收时间为主，并用 AUTH 的 `rx_callback_us + output_delay_us`
与主机接收时间估算时钟原点，完成尝试区间的近似对齐；这不是硬件同步。
`attempts.json` 标注了此对齐方式，`frames.csv` 同时保留主机接收时间和监听接收时间。
63 条 AP 回复都处于首轮第一次高功率窗口，不能按串口打印顺序判断实际空中先后。

两轮均启用错误帧观察；全程 `rx_error=0`、`suppressed=0`、
`error_queue_drops=0`、`queue_drops=0`，无 RX_ERROR 记录。
这些统计只覆盖驱动上交的帧，不证明空中没有损坏信号。
